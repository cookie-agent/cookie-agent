What I'd change

The Webhooks view works end to end: it creates, tests, reveals secrets, shows requests, and labels the sessions it starts. What it lacks is the guidance a first webhook needs, and a sense of health at a glance. Its form asks for typed syntax (hmac_sha256 header=…, json:/issue/number, filter lines). An open webhook is a 15-line key–value dump over seven buttons. Rejected requests are counted but never explained, and the phone layout breaks the event rows.

WBugs

W1 · Phone: an event's outcome is crushed to a few letters a line

The row's Open session button keeps its width, so "test · delivered · completed" wraps one syllable per line at 390 px.

W2 · Test events count nowhere

Uptime pings received three test events, yet its row says no requests yet. The counts leave tests out, and the row shows nothing else. Show the last event and its outcome.

W3 · "1 rejected", with no when or why

Rejected requests are only counted, by design (noise stays out of the history), but the counts carry last_rejected and the status each answer means. The row and details say only "1 rejected".

W4 · On or off, said twice

The "enabled" tag sits beside the switch that says the same. Keep a tag only for what the switch can't say: off after 5 failures.

W5 · "This URL only works here" in grey body text

The most important thing to know about a URL on 127.0.0.1 reads like a footnote, inside each webhook. Make it one amber callout above the list, with the way to fix it.

H1List rows: where it goes, how it's doing

  • A health line per row: a dot (green delivered, amber rejected recently, red failing, grey no events), the latest event with its time, and the last rejection with its reason in words (signature didn't match, bearer token wrong, over the hourly limit).
  • The target in words, with an arrow: "→ Deploy watch", a link; "→ new sessions · primary · one per issue.number".
  • An icon by preset (GitHub, Stripe, Bearer, Anything) instead of the same webhook glyph on every row; no check is an amber tag, since anyone with the URL can post.
  • The switch says on or off; Edit, Send a test event, and Delete are in ⋯ and right-click.
  • One amber callout above the list when the URLs are local only (W5).

H2An open webhook: a page, not a dump

  • Opening a webhook shows its own page (Back returns to the list): the name, check, and target under it, the switch, Send a test event, and ⋯ (Edit, New URL, New secret, Delete).

H4The form: presets and parts, not syntax

  • Start from GitHub, Stripe, Bearer token, or Anything. A preset fills the check, the filter, the thread key, and the headers shown, as cookie webhook create would with those flags.
  • Four steps: name and target; what the agent is told; who may send it; which requests count. Delivery, headers shown, and the limits fold under Advanced.
  • The check is a list (none, GitHub, Standard Webhooks, Bearer token, custom HMAC, the last opening header, encoding, and prefix fields). The secret says that cookie makes one unless you give your own.
  • Conditions are built from parts: header or JSON field, its name, the values as chips, with Edit as text for the line syntax. The thread key is "one session per: JSON field · header · event".

TTitles for the sessions a webhook starts

Today a webhook's sessions are titled after the webhook: GitHub issues · 2026-11-13 00:22, or GitHub issues · 42 with a thread key. A session title is now asked for when the webhook is made, in the form or by an agent through webhook_create, and takes the webhook name's place. Nothing is read from the requests into it. Or the model names each session after its first turn, as it does yours.
