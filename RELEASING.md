# Releasing Cookie Agent

Stable releases start from a GitHub release published by hand. cargo-dist
builds five Linux and macOS targets plus Windows x86_64 and ARM64 MSVC targets,
creates tar or ZIP archives and SHA256 checksums, generates shell and PowerShell
installers, and attaches those files to the published release. The workflow
also publishes the five public Rust crates when `CARGO_REGISTRY_TOKEN` is
configured in the repository's Actions secrets.

## Stable release

1. Update every workspace package version in `crates/*/Cargo.toml`.
2. Update every exact internal path dependency pin (`version = "=X.Y.Z"`) to
   the same version.
3. Run the full local verification suite and merge the version bump to `main`.
4. On GitHub, draft a new release with a new `vX.Y.Z` tag targeting the release
   commit on `main`, write the notes, and publish it.
5. Monitor the CI run for the `release` event and verify the attached artifacts.
6. Once the release's docs are published as `latest`, move links that point
   at `https://cookie-agent.github.io/doc/dev/` back to `doc/latest/`
   (`rg 'github.io/doc/dev/'`: `skills_command.rs`'s `DOCS_SITE`, the starter
   kit, the web client, and the official skills repository). Until a stable
   release carries the current docs, `latest` serves older pages.

Publishing fires the `release: published` event; drafts fire nothing. CI runs
every required check on the tag, then cargo-dist builds and uploads the
artifacts to the existing release, keeping its title and notes (dist's generated
notes fill in only when the body is empty). The release is public while that
run is in flight, so the installer URLs under `releases/latest` answer 404 until
the upload finishes. The tag's own push event does not start CI: pushes run for
branches only.

The workflow publishes crates in dependency order:
`cookie_agent_identity`, `cookie_agent_protocol`,
`cookie_agent_client_state`, `cookie_agent_web_assets`, then
`cookie_agent_plugin_sdk`. `cookie_agent_web_assets` carries the web client's
bundle: the workflow builds it once (`build-web`), every release binary embeds
it, and the release attaches it as `cookie-agent-web.tar.gz`. There is no
starter kit: daemons fetch the official agents from `cookie-agent/agents`
and the official skills from `cookie-agent/skills` themselves. It waits for each dependency version to appear in
the crates.io sparse index before publishing the dependent crate. Publication
finishes before the artifacts are uploaded. Each crate is skipped when its exact
version is already indexed, so rerunning a partially completed release resumes
at the first missing crate.

## Nightly release

The cargo-dist release workflow runs in release-branch mode. CI publishes at
most one nightly a day: its schedule (`.github/workflows/ci.yml`, 05:30 UTC)
runs every check on `main`'s head, and when they pass and that commit is not
already the newest nightly's, it calls the release workflow, which builds all
seven targets and creates a timestamped `vX.Y.Z-alpha.<timestamp>` prerelease
with shell and PowerShell installers. Each binary includes the source commit
in `cookie --version`.

Pushes to `main` run the same checks and publish nothing, so a commit is
published only by a run that checked it. A day without new commits publishes
nothing (the `Nightly due` job says why). To publish `main` sooner, dispatch
the CI workflow on `main` by hand (`gh workflow run ci.yml --ref main`); it
publishes under the same rules. A dispatch on any other branch runs the checks
only.

Nightlies trade binary size for build time. A stable release builds the
`dist` profile as `Cargo.toml` has it, fat LTO with one codegen unit; a
nightly overrides it with `CARGO_PROFILE_DIST_LTO=thin` and
`CARGO_PROFILE_DIST_CODEGEN_UNITS=16` in the `Build artifacts` step.

Measured on 2026-10-24 with `cargo build --profile dist -p cookie_agent`
(Linux x86_64, dependencies already built, as with CI's warm cache; the
workspace crates rebuilt with `-j 4` on four cores, about a CI runner):

| `lto` | `codegen-units` | Build | Binary |
| --- | --- | --- | --- |
| `fat` | 1 (stable releases) | 1008 s | 68.0 MB |
| `fat` | 16 | 968 s | 75.7 MB |
| `thin` | 1 | 609 s | 72.6 MB |
| `thin` | 16 (nightlies) | 468 s | 88.5 MB |

Fat LTO's single-threaded link is the cost, whatever the codegen units; thin
LTO with 16 units halves the build. A nightly is for testing and pruned
within two weeks, so its extra 20 MB is the cheaper side of that trade.

`.github/workflows/nightly-prune.yml` runs each Sunday at 04:00 UTC and can be
dispatched manually. It deletes nightly alpha releases and their tags after 14
days while always keeping at least the newest three. Nonmatching releases are
ignored.

### Regenerating the release workflow

`release.yml` is generated by cargo-dist 0.32.0, while `allow-dirty = ["ci"]`
protects the maintained edits. Move the workflow aside, temporarily remove the
`allow-dirty` entry, run `dist generate --mode=ci`, restore `allow-dirty`, then
reapply and review these edits:

- Plan published `release` events with `--tag=<release tag>` and every
  other call (CI's daily nightly) with `--tag=timestamp --force-tag`.
- In the `host` job, upload to the existing release for `release` events and
  keep `gh release create` for nightlies.
- Keep the workflow concurrency group, cancelling in progress for pull
  requests only: a publishing run is never interrupted.
- Keep root `contents: read` permissions and grant `contents: write` only to the
  `host` job that creates or fills the GitHub release.
- Install the pinned `dtolnay/rust-toolchain` action with toolchain `1.88.0`
  and the joined matrix targets instead of the generated Rust update step.
- Keep the SHA-pinned `Swatinem/rust-cache` step after toolchain installation,
  including the generated matrix target key and cache provider, with
  `save-if: ${{ github.event_name != 'release' }}`: a stable release's
  dependencies, built with fat LTO, could otherwise become the cache the
  nightlies restore and then rebuild.
- Set `retention-days: 2` on every dist scratch `upload-artifact` step: the dist
  cache, plan manifest, local artifacts, global artifacts, and final manifest.
- Set `COOKIE_GIT_HASH: ${{ github.sha }}` and
  `COOKIE_RELEASE_TAG: ${{ needs.plan.outputs.tag }}` in
  `build-local-artifacts`: the tag tells `cookie --version` and
  `cookie update` which channel a binary is on.
- Run `cargo metadata --locked --format-version=1` before `dist build`, and
  before it, outside `release` events, export `CARGO_PROFILE_DIST_LTO=thin`
  and `CARGO_PROFILE_DIST_CODEGEN_UNITS=16` (the nightly profile above).
- Keep the secret scan step after `Build artifacts`: on the
  `x86_64-unknown-linux-gnu` build it unpacks that archive and runs
  `release_binary_contains_no_secret_material` on the `cookie` binary inside
  (`COOKIE_RELEASE_BINARY`). A failed scan fails the build job, so `host` and
  `publish-crates` publish nothing.
- Preserve the `publish-crates` job, its `refs/tags/v` gate, and its
  `fromJson(needs.plan.outputs.val).announcement_is_prerelease == false` guard.
  The `host` job accepts that job being skipped for branch nightlies but still
  requires a successful crates publish for stable tags.

Nightly alpha releases and their tags are created with `GITHUB_TOKEN`; GitHub
does not start workflow runs for events created by that token, so nightly
generation never cascades into a stable release run.
